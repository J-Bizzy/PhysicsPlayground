# CLAUDE.md

**Physics Playground** — visionOS app. Room-scale physics labs, each fully volumetric and grabbable in the user's actual room. Portfolio project for college applications, so the physics must be genuinely correct: SI units, real constants, exact closed-form solutions where they exist, pure Swift with no physics libraries, tests written alongside the feature.

Deeper structure lives in `docs/ARCHITECTURE.md` — read it before adding a module or moving code between layers.

## Git safety

The git root is the parent directory, `~/Developer/VisionPro` (it was `Desktop/VisionPro` until the move; this paragraph named the old path until 2026-09-01). It holds sibling projects and a stray embedded repo (`cool/`, a gitlink that shows as `m ../cool` in every status). There is no `.git` inside this folder and there must never be one — `git init` here would nest a repo and orphan 430 commits of history. **Never `git add -A` or bare `git commit -m` from outside this project** — the index can carry pre-staged sibling files. Always commit with an explicit pathspec scoped to this project.

## Build & test

```bash
# Fast loop — pure physics, native on the Mac, no simulator:
cd Packages/PhysicsCore && swift test
cd Packages/PhysicsCore && swift test --filter MagneticFieldTests

# Full app build + app-level tests (needs the simulator):
xcodebuild test -project PhysicsPlayground.xcodeproj -scheme PhysicsPlayground \
  -destination 'platform=visionOS Simulator,name=Apple Vision Pro 4K'
```

Three suites, and the split is about what each CAN reach:
- `PhysicsCoreTests` — pure math, fast, no simulator.
- `PhysicsPlaygroundTests` — models, clamps, layout, and **tap handlers called directly**: build real entities, invoke `handleTap`, because no automation can synthesise a pinch. Four suites carry that pattern — `SpatialTapTests` (the picker), `SpatialActionBankTests`, `BloomPetalTests`, `MultimeterTests`. (Docs cited a `StationTapTests` here until 2026-08-02; no such file ever existed — the name is from the merged-worlds era, undone on 2026-07-30. The pattern outlived the name.)
- `PhysicsPlaygroundUITests` — real XCUITest taps on the **window** surfaces. Launch with `-uiTesting 1`, which gets the flat catalog on screen so XCUITest has something it can see; it cannot see anything in an immersive space. **What that argument DOES changed on 2026-08-22**: it used to suppress the window's automatic opening of the gallery, back when the window was the launch scene. The ImmersiveSpace is the launch scene now (`Info.plist`'s `UIApplicationPreferredDefaultSceneSessionRole`), and no launch argument can reach a static plist key — so `PlaygroundSpaceView.retreatForUITesting` turns round on the way IN and dismisses the space instead, letting the existing `onDisappear` hand the window back. It must not open the window itself: doing both produced two, with the catalog still up behind the module, which is precisely what `testTappingALabEntersIt`'s last assertion catches.

**Nothing automated can touch a RealityKit entity.** `simctl` has no tap verb and XCUITest has no entity API, so every spatial gesture — drag to the podium, pinch a magnet, two-hand zoom — is verified by hand against `docs/ON_DEVICE_TESTS.md`. A screenshot proves something rendered; it never proves it works.

**RUNNING FROM XCODE (2026-09-05).** A cold launch on this Mac, simulator freshly booted: the props warm in about a second (`PropCache.warmUp` loads the 42 bundled `.usdz` six at a time — sequential took five), the space is ready at ~1.4 s and the home stands at ~1.7 s. Debug builds say so in the console (`Shell/LaunchTrace.swift`): `[launch] +1.40 s  props warm: 41 assets in 0.94 s`, `[launch] +1.40 s  space ready, mounting the home`, `[launch] +1.65 s  home built in 0.24 s`. If those lines never come, the process is stopped, not slow. Three things to know: (1) `WorldTrackingProvider.isSupported` is TRUE in the simulator, so `RoomModel.retain()` runs a real `ARKitSession` there rather than taking the "nothing to run" exit, and a breakpoint anywhere in `retain()` pauses every launch the moment the gallery mounts — which looks exactly like an app that never opens. That is what happened on 2026-09-05: an enabled breakpoint at `RoomModel.swift:214`, kept in `xcuserdata`, so invisible to git and to every CLI run. **It happened again on 2026-09-06** — same breakpoint, still enabled in `xcuserdata/jacksonbizzell.xcuserdatad/xcdebugger/Breakpoints_v2.xcbkptlist`, and the console showed `space ready, mounting the gallery` with no `gallery built` line after it, followed by LLDB's `warning: PhysicsPlayground was compiled with optimization - stepping may behave oddly`. That warning is LLDB announcing that it has STOPPED the process in optimised code, and it is expected here: the Debug configuration builds with `SWIFT_OPTIMIZATION_LEVEL = -O` on purpose (commit 667e559, "optimize Debug builds"). Read the missing third line, not the warning: the fix is Xcode's Breakpoint navigator (⌘8), not the code. (2) The four lines at every start — `AddInstanceForFactory: No factory registered`, two `nw_socket_copy_info … TCP_INFO failed`, `TBB Global TLS count is not == 1` — are Apple's (CoreFoundation, Network, USD's Threading Building Blocks), print in every RealityKit app on the simulator, and mean nothing; `Logging Error: Failed to initialize logging system due to time out` is Xcode's log capture giving up on a busy simulator (`IDEPreferLogStreaming=YES` in the scheme's environment if it recurs). (3) RealityKit logs `Blocking engine queue waiting for AssetLoadRequest` at Default level for every synchronous mesh, material and collider generation — about 250 during the gallery build and ~1,000 on entering Circuit Workshop. Xcode's console hides them and Console.app does not; they are the cost of a `generate*` or a material on the main thread, not an error. Since 2026-09-05 every primitive mesh and collider comes from `RenderKit/Primitives` and every recipe in `Materials` is memoised (`PrimitiveCanonCriterionTests` fails a bare `generateSphere(` anywhere), which took Circuit Workshop's entry from ~1,000 blocks to a few hundred, most of them the extruded text of its nameplates.

**ORBITAL MECHANICS WAS RE-APPROACHED ON 2026-09-06** (and renamed from Gravity Lab the same day; its id `gravitylab`, the `-grav*` arguments and the `gravityAccent` token are unchanged). The integrator is a fourth-order symmetric symplectic composition (PEFRL, `NBody.step`), not velocity Verlet: leapfrog at the app's steps precessed an isolated Mercury 19″ per orbit at 1× and 119″ at ≥5×, RETROGRADE — 15× and 93× the real Newtonian rate, while conserving energy to 1e-8, and the device checklist called that creep "real Newtonian precession". `NBodyTests.testIsolatedMercuryDoesNotPrecessNumerically` pins it below 0.05″. The system has no net momentum (`settleMomentum` after every spawn, throw, edit and deletion; it used to drift 16 m/s), the substep follows the shortest two-body timescale present (`substepCount`, 6 h in the default system, capped at 96), a held body is `frozen` inside the integrator, merges are checked every substep, and each pair's softening floor is its merge distance. **A trail is `PhysicsCore.OrbitTrail`**: the trailing 0.75 of the body's own osculating period, sampled a degree apart about the heaviest body inside the substep loop, unwound (not redrawn) under reverse time, and drawn by `RenderKit.TrailRibbons` — ONE `LowLevelMesh` with a part per body, rewritten in place every frame and committed once (2026-10-17: a mesh per trail made twenty payloads a frame and left the main thread waiting on the renderer 58 % of the time), keyed by body id, 1.2 mm thick in the room at any zoom, fading to nothing at the tail through `Materials.fadedLine`. The old track-and-thumb-era trail (240 points at 8 mm for every body, rebuilt only when its point count changed) froze in space once full. The ring's tube is 1.4 mm in the room whatever the orbit or zoom and its mesh follows the exact eccentricity (`OrbitRing.canonicalRadii`/`needsRebuild`). Every body has its own colour (`celestialUI`, read by the textures' base fill so sphere and trail agree; `AccentAuthorityTests` holds ΔE ≥ 12); a world from the well is "World n" with a golden-angle hue. The Moon preset is gone (nine worlds): at 0.5 m/AU a bound Moon sits inside Earth's drawn sphere. **Its orbit ring is its centrepiece and cannot be pinched from the CLI**: `-selectBody <name>` picks the planet whose ring is drawn, and `-apsisDrag near|far,<factor>` actually RESHAPES that orbit — `-apsisDrag far,2.2` pulls apoapsis out to 2.2× its radius. Since 2026-10-14 nothing of its own but the world well stands in the room: the clock (six speeds), the overlays (velocity, net force, Kepler sweep, Lagrange points — the acceleration arrow was cut, it drew along the force), the nine-world "Add a world" grid, Twin suns and G are in the title bar's More (`-moreOpen 1`), and the star's and every planet's mass is a stretch grip on the body itself — pull the handle out and the body swells as the cube root (`Bloom.Grip.Stretch.surface`, shared with Electric Fields' charges). The sweep is OFF until asked for. `-gravRing 1` opens a body's control ring; `-predict 1` arms the ghost; `-gravClock <×>` (2026-09-06) sets the clock the picker would — one of `timeScales`, so `-gravClock 100 -pauseAfter 25` photographs the inner planets' trails full and Jupiter's filling in under a minute. `-gravLagrange 1` lights the Lagrange layer AND parks a body at L4, which is the only way to photograph the capture paragraph — like `-apsisDrag`, it reaches a capability rather than a control, because the paragraph appears on a RELEASE near a point and the simulator can neither pinch nor let go.

**WIRES ARE STRAIGHT (2026-08-29).** A connection is drawn taut between its terminals — the catenary sag (2026-08-11) is removed, owner's call: unnecessary. `Catenary.swift` is deleted from PhysicsCore, along with `slack(span:)` and the `-circSag` argument; the precedent was already in the house (the multimeter's probe leads were always straight). A wire is ONE unit-cylinder segment stretched by its transform, never a regenerated `TubeMesh`: the per-frame path touches only transforms, and a wire on a carried part moves every frame. **The segment carries no collider** — it encodes its length as a Y scale, and `ColliderCriterionTests` reads any collider under a world scale below 0.05 as a folded instrument it cannot honestly measure. The grab volume is one capsule on the unscaled parent, rebuilt only when an end moves 2 mm. `conductingPathLength` is the CHORD sum, which makes it identical by construction to the distances the true-speed field front walks — under sag the readout and the front disagreed (the front always walked chords). `CircuitsWirePathTests` holds this.

**TAP A LEAD AND ITS WHOLE NET LIGHTS (2026-08-11).** The one question a circuit builder asks constantly — *what is this connected to?* — had no answer in the room: a terminal wired through three hops looked exactly like a terminal wired to nothing. `highlightedNet` lights every terminal at that potential and every wire between them, in the module accent, over the top of the voltage ramp for as long as it is lit. It is **selection-driven, not hover**, and that is a limit rather than a preference: `HoverEffectComponent` is system-drawn with no callback and there is no hover event without `SpatialEventGesture`. Tapping empty space clears it, symmetric with the ring fold. It is an `Int?` and not a `Bool` deliberately — `ResetCoverageTests` reflects over `Bool`s and this is a selection, not a display layer — so `CircuitsNetHighlightTests` covers reset/clear/capsule by hand.

**A WIRE COMES OFF BY BEING PULLED OFF (2026-08-11).** `beginRewire` lifts one end of an existing wire into the same lead pull, drawn from the end that stayed — so moving a connection is one gesture instead of destroy-and-redraw. **The wire leaves `wires` the moment you lift it, and that is the teach, not an implementation detail:** the circuit goes dark in your hand, and a bulb going out as you lift a wire says what that wire was doing better than a label on it could. Three landings: another terminal rewires, the original terminal restores, open air deletes. A REFUSED rewire restores rather than deleting — losing a connection because you aimed at an illegal target is the harshest possible reading of a "no". The last three were undocumented everywhere until 2026-08-09. **`-circLegacyBench 1` is different in kind from all of them:** it writes a PRE-MIGRATION bench into `UserDefaults` from inside `CircuitsModel.init`, before the model reads it, because nothing else can stage a migration — the running app cannot mint a retired kind, and by the time any view has appeared the bench is already restored.

**WIRING IS ONE GESTURE: PULL A LEAD (2026-08-11).** There were three, on thresholds that disagreed — tap-tap (`tapTerminal`/`pendingTerminal`), drag-to-wire (a hardcoded 0.09 measured hand-to-terminal), and magnetic auto-connect on release (`snapDistance` 0.13). Two of them could fire from ONE EVENT: this view carries a single `DragGesture(minimumDistance: 0)` — it has to, because the rack pull must claim the first frame — so every tap also ran the drag, and a tap on a terminal armed the wiring through the tap gesture AND completed a different wire through the drag, in an order nothing defined. Tap-tap is deleted and `PressLatch` now gates the drag: a press promotes to a pull only past `tapTravel` (12 mm), so a zero-travel press cannot wire anything. **A tap selects; it never wires and never deletes** — tapping a wire used to destroy it outright, with no confirmation, on a bench that survives relaunch. The half-made wire lives in the MODEL as `LeadPull` (so `removeComponent` can cancel it — that is where the zombie-wire class died) and carries its `refusal` computed a frame BEFORE the release, so what you preview is what you get including the "no". **The refusal is a RECOIL, not a sentence:** the lead shortens back toward its source, goes red and thickens. Tap-tap survives for VoiceOver only, as `voiceOverWire`/`voiceWireSource` — named apart from `pendingTerminal` on purpose, and the pinch path never reads it. `CircuitsSpaceView.resolveGrab` is a pure static over entity names (following `FieldSpaceView.resolveCharge`) so the six-way priority order is testable without a headset, and it has **no distance fallback**: one part's two leads are 17 cm apart, so a fallback is how you wire the wrong end. **The RELEASE path speaks the same "no" (2026-08-29):** `release(id:)` returns an outcome and thuds when the only thing in reach was refused, and `refusedJoins(for:)` feeds the carry preview a RED ghost for a same-net terminal in reach — excluding pairs that already share a direct wire, so a part set back down in its own chain stays silent. **The switch lever gets the same 12 mm grace as everything else (2026-08-29):** a fourth `PressLatch` holds the press and `settle()` flips the switch at gesture end if it never travelled; the physical TapGesture only SELECTS a lever (both gestures complete on a clean tap, so a tap that also toggled would flip twice and read as a dead switch), and VoiceOver toggles through its own `onLeverAction` callback, which physical taps never fire.

**ONE GRAB TARGET AT EACH END (2026-08-11).** Every part used to carry FOUR touchable balls: a copper terminal at ±0.085 and an orange end grip at ±0.115, each with a 0.026 collision radius — 3 cm apart with hit volumes that overlapped, so which one you grabbed was decided by hit order. That is the "2 different nodes at each end" the owner reported. The grips are deleted; the copper lead is the only thing at an end. The body's carry target was a 0.075 sphere that swallowed the inner third of both lead colliders, and is now a box measured from the BODY (not the holder, which collects a bulb's glow and a selection halo) with its x half-extent clamped just inside the lead's inner edge at 0.059. Aiming, which was the grip's job, is a consequence of connection now: `CircuitsModel.swing` swings a part hanging by ONE wired lead about its JOINT — the anchor terminal at the far end of the wire, never the part's own lead, because the part's own lead moves with the part and pivoting on it after a move is the identity (which is exactly the defect that shipped until 2026-08-29: the view fed `swing` the part's just-moved centre and the affordance never happened). Within the body's own reach the lead sits exactly on the joint; past it the body tracks the hand while aiming its lead back at the joint, so the wire stretches — one continuous formula. **A wire never lets go because of distance (2026-09-05):** the 30 cm `breakDistance` pop is gone (moving the welcome circuit's parts kept breaking it, owner's report); a connection comes off only by pulling the wire's end off its terminal, cutting it, or deleting the part. The composition (swing, else move) lives in `CircuitsModel.drag(id:toward:)` so `CircuitsAlignmentTests` can drive the real sequence, and the per-frame gesture routing is `CircuitsSpaceView.carryDispatch` — a pure static like `resolveGrab`, because the closure once consulted the rack before the live carry and a rack-spawned part sat frozen at the rack until release (`CircuitsCarryDispatchTests` pins both the order and the Well trap that makes it load-bearing). `alignment(for:)`/`release(id:)` snap a released part nose-to-tail onto a neighbour's lead — moving and rotating it about the landing joint, never moving the target, which is also what stops a cascade. `leadReach` (0.06) is the single distance that replaced `snapDistance` 0.13 and a hardcoded 0.09 that disagreed about the same fact by 44%.

**THE JUMPER IS NOT A PART ANY MORE (2026-08-11).** `ComponentKind.wire` is retired: a *connection* spans any distance now, so a jumper part had nothing left to do, and the bench stops having two different things called "wire". Retiring a `Codable`-by-rawValue enum case is the dangerous half — decoding straight into `[Component]` throws for the WHOLE array on one unrecognised kind, and both restore paths swallow that with `try?`, so the naive deletion silently empties every saved bench and all eight named slots on first launch and the app looks like it is working. The bench is read through `StoredComponent`/`StoredBench` (kind as a raw `String`) and `migrated(_:)`, which SPLICES a retired part rather than dropping it — its two ends were one electrical point, so everything joined through it stays joined. `CircuitsBenchMigrationTests` holds this, and its last test uses a kind that never existed rather than the one just retired, so it goes on meaning something after `.wire` is history.

**A destructive verb arms before it fires.** Clear the bench, Clear all and Reset lab are `ControlButton(confirms: true)` in More, the launcher's Clear and a part's Delete are ring petals; each first tap swaps the title to "Tap again" for four seconds. None is staged from the CLI any more (`-emClear`, `-circClear` and `-paletteReset` went with the room plates and the palette on 2026-10-14) — a window button's armed state is its own `@State`. Orbital Mechanics' Twin suns is `-gravBinary 1`. **Pendulums has no verb at all.**

**The Time Capsule SHIPS ON** (`AppSettings.timeCapsule`, Settings → Time Capsule; owner's call 2026-09-01, reversing 2026-08-07 — the reel answered the "not always visible" objection the same day OFF was chosen, and OFF cost every buyer the app's most distinctive feature). The switch gates the RECORDING, not the reel — `TimeCapsuleSettings.isEnabled` is what every model's `recordCapsuleFrame` asks, so switched off nothing snapshots itself and the feature costs what it cost before it existed; switching it off mid-session drops whatever was recorded. **`-timeCapsule 0` switches it off for one launch** without writing the preference, which is how you photograph a plain pause; `-timeCapsule 1` is a no-op on a fresh install and still forces it on over a stored OFF. (This paragraph said SHIPS OFF and "every other argument is inert without `-timeCapsule 1`" from 2026-08-07 to 2026-09-01.)

**The Time Capsule's rail lives on a REEL, and the reel is what a pause shows.** Pausing puts one modelled reel (`Models/Shell/TimeReel.usdz`, built by `Tools/timereel.py`) in front of the apparatus; a pinch draws the rail out of it and a second pinch winds it in. The rail is never on screen unasked — that was the owner's objection to the first build, and `TimeRailTests` holds the line. The reel also TURNS with the scrub, so the closed object is a readout, not a lid. Because the simulator cannot pinch, **`-scrubBack` draws the tape out as well as scrubbing**; to photograph the reel closed, pass `-pauseAfter` alone, since that is what a pause actually looks like.

**The Time Capsule (2026-08-07) is the one feature that spans every module.** Every model conforms to `TimeCapsuleRecording` (`Shell/TimeCapsuleSupport.swift`): it records an `Equatable` snapshot of itself into a `PhysicsCore.TimeCapsule` ring buffer at the end of every unpaused `step`, and the shell's one `TimeRail` (`Shell/TimeRail.swift`, mounted in `PlaygroundSpaceView`) scrubs it while paused. Three rules govern additions:
- **Recording happens inside the model's `step`, in a function-scope `defer`** — never in a SpaceView, because models outlive the views and existing tests drive `step` directly.
- **The snapshot is the experiment, not the observer.** Dynamical state and entity sets in; display layers, bank flags and selections out. The stated exception is Electric Fields, where `capacitorOn`/`magneticFieldOn`/`chargesRespond` change the physics the recorded motion happened in.
- **Never snapshot an unbounded array.** Orbital Mechanics' orbit trails and Electric Fields' probe trail are rebuilt FROM the capsule on restore, under the same rules the live code applies (for the trails: the trailing 0.75 of each body's own period, sampled a degree apart, spliced with the live samples stashed when the scrub began).
**Reading a snapshot's field list is not the check** — the same attention that writes the list is the one that forgets a field. `TimeCapsuleRoundTripTests`'s replay tests restore to mid-window, re-step with the identical dt sequence, and diverge measurably if any dynamical field is missing.

**When a toggle becomes a switch plate, check `reset()` restores the flag behind it.** **SIX** modules have had that defect — four found on 2026-07-31, and Orbital Mechanics' `keplerSweepOn` and Electric Fields' `chargesRespond` on 2026-08-03, behind lit plates, after this paragraph already existed. A flag with no visible control drifts out of `reset()` and stays wrong because nothing in the room contradicts it; the moment it gets a lamp, the lamp makes the claim every frame. **Reading `reset()` is no longer the check** — every previous fix was a test that LISTED the flags somebody had thought of, which is the same act of attention that missed them. `ResetCoverageTests` reflects over each model, finds every `Bool`, and asserts a mutated-then-reset model matches a fresh one. Add a flag and it is covered; you will be told to add a `flip` case rather than trusted to remember.
